## 2. 실험 조건

- **데이터 생성:** 이전 과제와 같은 코드(`srand(12345)` 후 `rand() % 100000`)로 무작위 정수를 생성합니다. 시드가 고정되어 있어 다시 실행해도 같은 데이터가 나옵니다.
  - 참고: `rand()`의 구현은 운영체제(C 라이브러리)마다 다릅니다. 따라서 다른 환경에서 실행하면 생성 코드가 같아도 데이터 값과 비교 횟수가 달라질 수 있습니다. 이번 결과는 모두 아래 환경 한 곳에서 측정했으며, 다섯 알고리즘은 같은 데이터를 사용했습니다.
- **데이터 크기:** n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- **중복 허용:** 값 범위가 0~99,999이므로 중복된 값이 일부 생깁니다.
- **동일 입력 보장:** 각 크기마다 원본 배열을 하나 만들고, 알고리즘마다 `memcpy`로 복사한 배열을 정렬합니다.
- **정렬 방향:** 오름차순입니다.
- **실험 환경:** Apple M5 (arm64), Apple clang 21.0.0, `-O2`. L1 데이터 캐시는 64KB, L2 캐시는 6MB입니다.

## 3. 힙 정렬 구현

```c
static void sift_down(int a[], int root, int size)   /* 반복문으로 힙 속성 복구 */
static void heap_sort(int a[], int n)
{
    for (i = n / 2 - 1; i >= 0; i--) sift_down(a, i, n);  /* 1) 최대 힙 구성 */
    for (end = n - 1; end > 0; end--) {
        swap_int(&a[0], &a[end]);                         /* 2) 루트(최댓값) ↔ 마지막 원소 */
        sift_down(a, 0, end);                             /* 3) 힙 크기 감소 후 복구 */
    }
}
```

- 입력 배열 자체를 최대 힙으로 사용합니다. 인덱스 `i`의 자식은 `2i+1`, `2i+2`입니다. 별도의 힙 배열은 만들지 않습니다.
- 힙 구성은 마지막 내부 노드(`n/2 - 1`)부터 루트까지 아래로 내려가며 정리하는 상향식(Floyd) 방법을 사용합니다. 이 단계는 O(n)입니다.
- `sift_down`은 재귀 대신 `while` 반복문으로 구현했습니다. 그래서 호출 스택이 n과 관계없이 일정합니다.

## 4. 측정 방법

### 4.1 숫자 비교 횟수
- **힙 정렬:** `sift_down` 안의 두 가지 값 비교를 모두 셉니다. 힙 구성 단계와 정렬(복구) 단계 모두 포함됩니다.
  1. 두 자식 중 큰 쪽을 고르는 `a[child] < a[child+1]` 비교 (오른쪽 자식이 있을 때만)
  2. 부모와 큰 자식을 비교하는 `a[root] < a[child]` 비교
- **병합 정렬:** 병합 과정의 `a[i] <= a[j]` 비교를 셉니다.
- **퀵 정렬(Lomuto 분할):** 분할 과정의 `a[j] < pivot` 비교를 셉니다. Median-of-Three는 피벗을 고를 때 쓰는 값 비교(2~3회)도 더합니다.
- **제외 항목:** 반복문의 인덱스 및 종료 조건 검사(`child < size`, `i <= mid` 등), 무작위 위치 생성, 원소 교환과 복사는 세지 않습니다.

### 4.2 실행시간
- 정렬 함수 호출 직전과 직후에 `clock()`을 호출하고, 그 차이를 ms로 환산합니다. 다섯 알고리즘 모두 같은 방법을 사용합니다.
- 데이터 생성, 배열 복사(`memcpy`), 정렬 확인, 결과 출력은 측정 구간에 넣지 않았습니다.
- 한 번만 실행하면 시간이 너무 짧아 오차가 크므로, 같은 데이터로 20회 실행한 평균을 기록했습니다.

### 4.3 메모리 사용량 (계산 기준)
프로파일러를 쓰지 않고 **직접 계산**했습니다. 원본 데이터 배열은 공통 비용이므로 제외하고, 정렬 중 추가로 필요한 최대 메모리만 셉니다.

| 알고리즘 | 계산식 | 비고 |
|---|---|---|
| 힙 정렬 | `heap_sort` 프레임 + `sift_down` 프레임 | 재귀가 없으므로 동시에 존재하는 프레임은 최대 2개 |
| 병합 정렬 | 임시 배열 `n × sizeof(int)` + 최대 재귀 깊이 × 28 | 이전 과제와 동일 |
| 퀵 정렬 | 최대 재귀 깊이 × 20 | 보조 배열 없음, 이전 과제와 동일 |

- **프레임 크기 기준:** 함수 인자와 지역 변수의 크기를 더했습니다 (`sizeof(int*)` = 8, `sizeof(int)` = 4).
  - `heap_sort`: 배열 포인터 + `n`, `i`, `end` = 8 + 12 = **20 Byte**
  - `sift_down`: 배열 포인터 + `root`, `size`, `child`, `tmp` = 8 + 16 = **24 Byte**
  - 힙 정렬 합계: **44 Byte** (n과 무관)
  - 병합 정렬 프레임: 포인터 2개 + 정수 3개 = 28 Byte, 퀵 정렬 프레임: 포인터 1개 + 정수 3개 = 20 Byte
- **최대 재귀 깊이:** 병합 정렬과 퀵 정렬은 정렬 중에 `cur_depth`로 재귀 깊이를 추적해 그 최댓값을 사용했습니다.
- 실제 컴파일러는 레지스터 사용, 반환 주소, 정렬(alignment), 인라인화 때문에 이 값과 다른 스택을 쓸 수 있습니다. 실제로 `-O2`에서는 `heap_sort`와 `sift_down`이 `main`에 인라인되었습니다. 그래서 이 값은 **알고리즘 간 상대 비교용 추정치**로 보아야 합니다.

## 6. 분석

### 6.1 데이터 크기 증가에 따른 비교 횟수 변화

n이 2배가 될 때 비교 횟수가 몇 배가 되었는지 정리했습니다. 이론상 n log₂n 은 n이 2배가 되면 약 2.1~2.2배가 됩니다.

| 구간 | n log₂n 증가율 | Heap | Merge | Quick(First) | Quick(Random) | Quick(Median3) |
|---|---:|---:|---:|---:|---:|---:|
| 1,000 → 2,000 | 2.20 | 2.25 | 2.23 | 2.25 | 2.31 | 2.13 |
| 2,000 → 4,000 | 2.18 | 2.21 | 2.21 | 2.30 | 2.32 | 2.24 |
| 4,000 → 8,000 | 2.17 | 2.19 | 2.19 | 2.19 | 2.17 | 2.15 |
| 8,000 → 16,000 | 2.15 | 2.17 | 2.17 | 2.09 | 2.19 | 2.24 |
| 16,000 → 20,000 (×1.25) | 1.28 | 1.28 | 1.28 | 1.27 | 1.29 | 1.27 |

- 세 알고리즘 모두 증가율이 n log n과 거의 같습니다. 세 알고리즘 모두 평균 O(n log n)이라는 것을 실험으로 확인했습니다.
- 그러나 **상수(계수)는 크게 다릅니다.** 20,000개에서 비교 횟수를 n log₂n(≈ 285,754)으로 나누면 다음과 같습니다.
  - 병합 정렬 **0.91**, 퀵 정렬 **1.11~1.21**, 힙 정렬 **1.79**
- **힙 정렬이 가장 많이 비교하는 이유:** `sift_down`은 한 층 내려갈 때마다 비교를 **2번** 합니다. 두 자식 중 큰 쪽을 고르는 비교 1번과, 그 자식과 부모를 비교하는 1번입니다. 또 정렬 단계에서는 힙의 **마지막 원소(작은 값)** 를 루트로 올린 뒤 내립니다. 이 값은 거의 항상 잎 근처까지 내려가므로, 매번 약 log₂n 층을 지나며 2log₂n 번 비교합니다. 그래서 전체 비교 횟수가 약 2n log₂n에 가까워집니다(실측 1.79배). 반면 힙 구성 단계는 O(n)이므로 전체에서 차지하는 비중이 작습니다.
- **병합 정렬이 가장 적게 비교하는 이유:** 병합할 때 원소 하나를 결과에 넣으려면 비교가 최대 1번 필요합니다. 한쪽이 먼저 끝나면 나머지는 비교 없이 복사합니다. 그래서 비교 횟수가 이론적 하한(log₂ n!)에 가깝습니다.
- **퀵 정렬:** 분할 한 번에 (구간 길이 − 1)번 비교하므로 분할이 고를수록 비교가 적습니다. 무작위 데이터에서 평균은 약 1.39 n log₂n로 알려져 있지만, Lomuto 방식에서는 크기 1 이하 구간을 바로 반환하므로 실측은 이보다 조금 작은 1.1~1.2배였습니다.

### 6.2 실행시간 차이

| n | Heap | Merge | 가장 빠른 Quick |
|---:|---:|---:|---:|
| 1,000 | 0.0422 | 0.0483 | 0.0205 (Median3) |
| 4,000 | 0.1157 | 0.1894 | 0.1793 (Median3) |
| 8,000 | 0.2474 | 0.3419 | 0.2601 (Median3) |
| 16,000 | 0.3509 | 0.5138 | 0.4562 (Median3) |
| 20,000 | 0.3606 | 0.5524 | 0.5482 (First) |

- **비교 횟수 순서와 실행시간 순서가 다릅니다.** 힙 정렬은 비교를 가장 많이 했지만(병합 정렬의 약 2배), n ≥ 4,000에서는 가장 빨랐습니다. 20,000개에서 힙 정렬은 0.36ms, 병합 정렬과 퀵 정렬은 0.55~0.62ms였습니다. 같은 프로그램을 3번 더 실행해도 힙 정렬은 0.37~0.39ms로 매번 가장 빨랐습니다.
- 비교 1회당 시간으로 바꾸면 힙 정렬은 약 0.7ns, 퀵 정렬은 약 1.7~1.9ns, 병합 정렬은 약 2.1ns입니다. 즉 이 실험에서는 **비교 횟수보다 비교 1회의 비용**이 실행시간을 결정했습니다. 그 원인은 다음과 같이 분석했습니다.
  1. **분기 예측:** 무작위 데이터에서 퀵 정렬의 `a[j] < pivot`과 병합 정렬의 `a[i] <= a[j]`는 결과가 거의 50:50입니다. CPU가 결과를 미리 예측하기 어려워 예측 실패 비용이 큽니다. 힙 정렬의 "큰 자식 고르기"는 컴파일러가 분기 없는 `csel` 명령으로 바꾸었습니다(`-S` 출력으로 확인). 또 "부모 < 자식" 비교는 정렬 단계에서 대부분 참(계속 내려감)이어서 예측이 잘 맞습니다.
  2. **캐시:** 힙 정렬은 부모와 자식(2i+1) 사이를 오가므로 메모리 접근이 흩어집니다. 데이터가 커지면 캐시 효율이 나빠지는 것이 힙 정렬의 일반적인 약점입니다. 하지만 이번 실험의 최대 데이터는 20,000 × 4 Byte = 80KB입니다. 이는 L2 캐시(6MB) 안에 모두 들어가는 크기라서 약점이 드러나지 않았습니다.
  3. **데이터 이동량:** 병합 정렬은 단계마다 n개를 임시 배열로 옮기고 다시 원본으로 복사하므로, 이동량이 가장 많습니다. 그래서 비교 횟수가 가장 적어도 퀵 정렬과 비슷하거나 더 느렸습니다.
- 따라서 "힙 정렬이 퀵 정렬보다 항상 빠르다"는 결론은 내릴 수 없습니다. 데이터가 캐시보다 훨씬 큰 경우나 다른 CPU와 컴파일러에서는 결과가 달라질 수 있습니다. 교과서에서 보통 퀵 정렬이 힙 정렬보다 빠르다고 설명하는 이유도 큰 데이터에서의 캐시 지역성 때문입니다.
- 크기가 작을 때(1,000개)는 시간 자체가 0.02~0.05ms로 매우 짧아 측정 오차가 상대적으로 큽니다. 퀵 정렬 세 방식 사이의 차이(0.1ms 이하)도 반복 실행마다 순위가 바뀔 정도로 작습니다.

### 6.3 메모리 사용량 차이

| n | Heap | Merge | Quick (First / Random / Median3) |
|---:|---:|---:|---:|
| 1,000 | 44 | 4,280 | 520 / 400 / 300 |
| 20,000 | 44 | 80,420 | 640 / 640 / 500 |

- **힙 정렬: O(1), 44 Byte로 일정합니다.** 입력 배열 자체를 힙으로 쓰고 `sift_down`을 반복문으로 구현했기 때문에, 보조 배열도 없고 재귀 스택도 늘어나지 않습니다.
- **병합 정렬: O(n).** 임시 배열(n × 4 Byte)이 대부분을 차지합니다. n이 20배가 되면 메모리도 약 19배(4,280 → 80,420)로 늘었습니다. 20,000개에서는 힙 정렬의 약 1,800배입니다.
- **퀵 정렬: O(log n).** 보조 배열은 없지만 재귀 깊이만큼 스택을 씁니다. n이 20배가 되어도 300~520 Byte에서 500~640 Byte로 조금만 늘었습니다. 최대 재귀 깊이는 25~32 정도로, log₂(20,000) ≈ 14.3의 약 2배입니다. 분할이 완전히 균등하지 않기 때문입니다.
- Median-of-Three가 대체로 메모리가 가장 적었습니다. 분할이 더 균형 잡혀서 재귀 깊이가 얕아졌기 때문입니다.

### 6.4 퀵 정렬의 피벗 선택 방법에 따른 차이
- **Median-of-Three**는 2,000개 이상의 모든 크기에서 비교 횟수가 가장 적었습니다. 20,000개에서 316,162회로 First보다 2.7%, Random보다 8.5% 적었습니다. 세 값의 중앙값을 피벗으로 쓰면 극단적인 피벗이 뽑힐 가능성이 줄어 분할이 고르게 됩니다. 피벗 선택에 2~3번의 비교가 더 들지만, 분할이 좋아져서 줄어드는 비교가 더 많습니다. 재귀 깊이도 가장 얕아 메모리가 가장 적었습니다.
- **First**는 이번 데이터가 이미 무작위이므로 첫 원소도 사실상 무작위 피벗입니다. 그래서 Random과 비슷한 성능을 냈습니다. 하지만 정렬되었거나 거의 정렬된 입력에서는 매번 최솟값이 피벗이 되어 O(n²) 비교와 O(n) 재귀 깊이로 나빠집니다. 이 경우는 이번 실험에 포함하지 않았습니다.
- **Random**은 입력 순서와 관계없이 평균 O(n log n)을 보장하는 것이 장점입니다. 무작위 데이터에서는 First보다 나은 점이 없었고, 20,000개에서는 오히려 가장 많이 비교했습니다. 이는 난수 결과에 따른 차이입니다.
- 세 방식의 실행시간 차이는 측정 오차 범위 안에 있어서, 순위를 정하기 어렵습니다.

### 6.5 시간 복잡도 및 공간 복잡도 비교

| 항목 | 힙 정렬 | 병합 정렬 | 퀵 정렬 |
|---|---|---|---|
| 최선 시간 | O(n log n) | O(n log n) | O(n log n) |
| 평균 시간 | O(n log n) | O(n log n) | O(n log n) |
| 최악 시간 | **O(n log n)** | **O(n log n)** | O(n²) |
| 추가 공간 | **O(1)** | O(n) | 평균 O(log n), 최악 O(n) |
| 안정 정렬 | 불안정 | 안정 | 불안정 |
| 실측 비교 횟수 (n=20,000) | 약 1.79 n log₂n | 약 0.91 n log₂n | 약 1.11~1.21 n log₂n |
| 실측 추가 메모리 (n=20,000) | 44 B | 80,420 B | 500~640 B |

- **힙 정렬**은 최악의 경우에도 O(n log n)이고 추가 메모리도 O(1)입니다. 다만 비교 횟수의 상수가 가장 크고, 데이터가 클 때 캐시 지역성이 나쁘며, 안정 정렬이 아닙니다.
- **병합 정렬**은 비교 횟수가 가장 적고 최악에도 O(n log n)이며 안정 정렬입니다. 대신 O(n) 추가 메모리와 복사 비용이 듭니다.
- **퀵 정렬**은 평균적으로 빠르고 메모리도 적지만, 피벗 선택이 나쁘면 최악 O(n²)이 될 수 있습니다.

## 7. 결론
1. **비교 횟수:** 세 알고리즘 모두 n log n 비율로 증가했습니다. 상수는 병합(0.91) < 퀵(1.1~1.2) < 힙(1.79) 순입니다. 힙 정렬은 한 층마다 비교를 2번 하고, 정렬 단계에서 작은 값을 루트에서 잎까지 내리기 때문에 비교가 가장 많습니다.
2. **실행시간:** 이번 환경(Apple M5, 데이터 ≤ 80KB)에서는 비교가 가장 많은 힙 정렬이 가장 빨랐습니다. 분기 없는 코드와 예측하기 쉬운 비교 덕분에 비교 1회의 비용이 작았고, 데이터가 캐시 안에 들어가서 힙의 캐시 약점이 드러나지 않았습니다. 병합 정렬은 비교가 가장 적었지만 데이터 복사 때문에 가장 느린 편이었습니다. 비교 횟수만으로 실행시간을 예측할 수 없다는 것을 확인했습니다.
3. **메모리:** 힙 O(1)(44 B) < 퀵 O(log n)(≤ 640 B) < 병합 O(n)(≈ 80 KB) 순입니다. 각 알고리즘의 구조(제자리 힙, 재귀 분할, 임시 배열)가 그대로 반영되었습니다.
4. **한계:** 실행시간은 한 환경에서 20회 평균으로 측정했고, 메모리는 계산으로 구한 추정치입니다. 무작위 데이터만 사용했으므로 퀵 정렬의 최악 경우와, 캐시보다 큰 데이터에서의 힙 정렬 성능 저하는 확인하지 못했습니다.
