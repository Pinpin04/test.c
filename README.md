# 과제 15: 퀵 정렬과 AVL 트리 정렬의 성능 비교

## 1. 파일 구성

| 파일 | 설명 |
|---|---|
| `quick_vs_avl.c` | 배열 + 퀵 정렬, AVL 트리 정렬, 삽입·삭제 실험 및 성능 측정 프로그램 |
| `result.txt` | 프로그램 실행 결과 원문 |
| `README.md` | 본 문서 |

컴파일 및 실행 방법:

```bash
gcc -O2 -Wall -o quick_vs_avl quick_vs_avl.c
./quick_vs_avl > result.txt
```

## 2. 실험 조건

- **데이터 생성:** 이전 과제와 같은 방식으로 `srand(12345)` 후 `rand() % 100000`을 사용했습니다. 그래서 정렬 단계의 퀵 정렬 비교 횟수가 과제 14의 Quick (Median3) 결과와 같습니다(예: 20,000개에서 316,162회).
- **데이터 크기:** n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- **중복 허용:** 값 범위가 0~99,999이므로 중복 값이 생깁니다.
- **동일 입력:** 각 크기마다 원본 배열을 하나 만들고, 두 방법이 모두 이 배열을 사용합니다.
- **실험 환경:** Apple M5 (arm64), Apple clang 21.0.0, `-O2`

### 2.1 퀵 정렬의 피벗 선택 방법: **Median-of-Three**
과제 14에서 비교 횟수와 재귀 깊이가 가장 작았던 방법입니다. 또 이미 정렬된 입력에서도 O(n²)으로 나빠지지 않습니다. 그래서 이 방법을 선택했습니다. 코드는 과제 13/14의 퀵 정렬(Lomuto 분할)을 그대로 사용했습니다.

### 2.2 삽입·삭제 연산 생성
- 연산 횟수는 m = n × 20%입니다 (200 / 400 / 800 / 1,600 / 3,200 / 4,000회).
- 연산을 만들 때 난수를 2개 사용합니다.
  1. 첫 번째 난수(`rand()`)가 짝수면 **삽입**, 홀수면 **삭제**입니다.
  2. 두 번째 난수(`rand() % 100000`)를 삽입하거나 삭제할 **값**으로 사용합니다.
- 연산 목록은 측정을 시작하기 전에 별도의 시드(`srand(54321)`)로 미리 만들어 둡니다. 두 자료구조에는 **같은 연산 목록을 같은 순서로** 적용합니다. 난수 생성 시간은 측정에 포함되지 않습니다.
- 삭제할 값이 없으면 아무것도 하지 않고 다음 연산으로 넘어갑니다. 값이 0~99,999 범위의 난수이므로 삭제가 실패하는 경우가 많습니다. 예를 들어 20,000개에서는 삭제 1,969회 중 386회만 실제로 값을 찾았습니다. 그래서 최종 데이터 개수는 n보다 늘어납니다.

### 2.3 두 자료구조의 구현
| | 배열 + 퀵 정렬 | AVL 트리 |
|---|---|---|
| 정렬 | 퀵 정렬로 오름차순 정렬 | n개의 값을 차례로 AVL 트리에 삽입 |
| 삽입 | 앞에서부터 선형 탐색해서 `a[i] > x`인 첫 위치를 찾음 → 그 뒤 원소를 한 칸씩 뒤로 이동 → `a[i] = x` | 루트부터 비교하며 내려감. 같은 값이 있으면 `count++`, 없으면 새 노드 생성 → 올라오면서 회전으로 균형 복구 |
| 삭제 | 선형 탐색으로 `a[i] >= x`인 첫 위치를 찾음 → `a[i] == x`이면 뒤 원소를 앞으로 한 칸씩 이동 | 값을 찾아 `count > 1`이면 `count--`. 아니면 노드를 삭제(자식이 2개면 오른쪽 최솟값으로 대체) → 회전으로 균형 복구 |
| 중복 처리 | 같은 값을 배열에 여러 번 저장 | 노드의 `count` 필드에 중복 개수를 저장 |

- 배열의 삭제 탐색은 배열이 정렬되어 있으므로 `x`보다 큰 값을 만나면 바로 멈춥니다(값 없음).
- AVL 노드 구조: `int key, count, height` + `Node *left, *right` = **32 Byte**(정렬 패딩 포함, `sizeof(Node)`로 확인)

### 2.4 정확성 확인 (측정 구간 밖)
- 퀵 정렬 직후 배열이 오름차순인지 확인했습니다.
- AVL 트리에 n개를 삽입한 직후 **중위 순회** 결과(중복 개수만큼 펼침)가 퀵 정렬 결과와 같은지 확인했습니다.
- 모든 삽입·삭제가 끝난 뒤에도 AVL 중위 순회 결과와 배열이 **원소 하나하나까지 같은지** `memcmp`로 비교했습니다.
- 6개 크기 모두 통과했습니다(`Overall verification : ALL OK`). 최종 데이터 개수도 두 자료구조가 같습니다.

## 3. 측정 방법

### 3.1 총 수행시간
- 측정 구간은 정렬 시작부터 마지막 삽입·삭제 완료까지입니다. 시작 직전과 완료 직후에 `clock()`을 호출해 ms로 환산했습니다.
- 데이터·연산 난수 생성, 원본 복사, 정확성 확인, 트리 해제(`free`), 결과 출력은 측정에서 제외했습니다.
- AVL 트리의 노드 생성(`malloc`)과 삭제(`free`)는 자료구조 동작의 일부이므로 시간에 포함했습니다.
- 시간이 짧으면 오차가 크므로 같은 과정을 20번 반복한 평균을 사용했습니다.

### 3.2 비교 횟수 (데이터 값 비교만)
- **퀵 정렬:** 분할의 `a[j] < pivot`, Median-of-Three의 값 비교 2~3회를 셉니다.
- **배열 삽입·삭제:** 선형 탐색의 `a[i] > x` / `a[i] >= x`, 삭제 시 `a[i] == x` 확인을 셉니다.
- **AVL:** 노드마다 `x < key`를 비교하고, 거짓이면 `x > key`를 한 번 더 비교합니다. 즉 왼쪽으로 가면 1회, 오른쪽으로 가거나 같은 값을 찾으면 2회입니다.
- **제외:** 반복문 인덱스·종료 조건(`i < count`), 높이와 균형 인수 비교, NULL 검사는 데이터 값 비교가 아니므로 세지 않습니다.

### 3.3 데이터 이동 횟수 (데이터 값의 복사·대입)
- **퀵 정렬:** `swap` 1회 = 3회(tmp ← a, a ← b, b ← tmp), 피벗 값 복사(`pivot = a[hi]`) 1회입니다.
- **배열 삽입·삭제:** 원소를 한 칸 옮길 때마다 1회, 새 값 대입 1회입니다.
- **AVL:** 새 노드에 값을 저장(`key = x`)할 때 1회, 자식이 2개인 노드를 삭제할 때 후계자 값을 복사할 때 1회입니다.
- **제외:** 회전과 연결 변경 같은 **포인터 대입**, 중복 개수(`count`)와 높이(`height`) 갱신은 데이터 값이 아니므로 세지 않습니다.

### 3.4 메모리 사용량 (계산 기준)
과제 14와 같이 **직접 계산**했습니다. 과제 15는 자료구조 자체도 포함해야 하므로 데이터 저장 공간도 넣었습니다.

| | 계산식 |
|---|---|
| 배열 | max( 정렬 중: `n × 4` + 최대 재귀 깊이 × 20,  삽입·삭제 중: 최대 원소 수 × 4 ) |
| AVL | 최대 노드 수 × 32 + 최대 재귀 깊이 × 16 |

- 배열의 정렬 단계 재귀 스택은 정렬이 끝나면 사라지므로, 두 단계 중 큰 값을 최대 사용량으로 보았습니다.
- 퀵 정렬 프레임 20 Byte(포인터 1 + 정수 3)는 과제 14와 같은 기준입니다. AVL 재귀 프레임은 노드 포인터와 값을 합해 16 Byte(8 + 4, 8 Byte 정렬)로 두었습니다.
- AVL의 노드 수는 **서로 다른 값의 개수**입니다. 중복 값은 `count`만 늘리므로 노드가 늘지 않습니다.
- `malloc` 내부 관리 정보와 실제 스택 프레임 크기는 환경에 따라 다릅니다. 그래서 이 값은 상대 비교를 위한 추정치입니다.

## 5. 분석

### 5.1 총 수행시간과 비교 횟수의 차이
- **정렬 단계만 보면 퀵 정렬이 유리합니다.**
  - 비교 횟수는 퀵 정렬이 316,162회, AVL이 386,299회로 퀵 정렬이 약 18% 적습니다. AVL은 오른쪽으로 내려갈 때 `x < key`와 `x > key`를 두 번 비교하기 때문입니다. 또 트리 높이가 최적보다 조금 높을 수 있습니다.
  - 시간은 퀵 정렬이 약 0.69ms, AVL이 약 1.41ms로 퀵 정렬이 약 2배 빠릅니다. AVL은 노드를 만들 때마다 `malloc`을 호출하고, 포인터를 따라 흩어진 메모리를 읽으며, 회전도 합니다. 배열은 연속된 메모리를 차례로 읽으므로 캐시 효율이 좋습니다.
- **삽입·삭제가 들어가면 결과가 뒤집힙니다.**
  - 20,000개 전체 과정에서 비교 횟수는 배열 4,187만 회, AVL 47만 회로 **약 89배** 차이가 납니다. 총 시간은 11.08ms 대 1.79ms로 AVL이 **약 6.2배** 빠릅니다.
  - 배열의 전체 비교 중 **99% 이상**(4,156만 / 4,187만)이 정렬이 아니라 삽입·삭제의 선형 탐색에서 나왔습니다. 배열은 정렬되어 있어도 앞에서부터 하나씩 비교하므로, 연산 1번에 평균 약 10,389번 비교합니다. 이는 현재 원소 수(약 2만)의 절반 정도입니다.
  - AVL은 높이가 O(log n)으로 유지되므로 연산 1번에 평균 21.4번만 비교했습니다. log₂(20,000) ≈ 14.3이고, 노드마다 비교를 1~2번 하므로 이론값과 맞습니다.
- **n = 1,000에서는 배열이 더 빨랐습니다**(0.10ms 대 0.14ms). 이 크기에서는 배열의 선형 탐색이 짧고, AVL의 노드 할당 비용이 상대적으로 큽니다. n = 2,000부터 AVL이 앞섰습니다.

### 5.2 삽입·삭제 과정의 데이터 이동 횟수 차이
- 20,000개에서 삽입·삭제 4,000회 동안 배열은 **2,530만 회**, AVL은 **1,812회** 데이터를 이동했습니다. 약 14,000배 차이입니다.
- **배열:** 정렬 상태를 유지하려면 원소들이 연속해서 저장되어 있어야 합니다. 삽입하면 그 위치 뒤의 모든 원소를 한 칸 뒤로, 삭제하면 뒤의 모든 원소를 한 칸 앞으로 옮겨야 합니다. 그래서 삽입 1회에 평균 n/2번 이동이 생깁니다. 삽입에서는 "탐색한 칸 수 + 이동한 칸 수 = 현재 원소 수"이므로, 데이터가 많을수록 삽입 비용이 그대로 커집니다.
- **AVL:** 노드끼리 포인터로 연결되어 있으므로, 새 노드를 만들어 연결만 하면 다른 데이터는 그대로 둡니다. 균형을 복구하는 회전도 **포인터 몇 개만 바꾸고 데이터 값은 옮기지 않습니다.** 실제로 값이 복사되는 경우는 두 가지뿐입니다.
  1. 새 노드에 값을 저장할 때(1회)
  2. 자식이 2개인 노드를 삭제할 때 후계자 값을 복사할 때(1회)
  - 중복 값의 삽입과 삭제는 `count`만 바꾸므로 이동이 0회입니다. 그래서 연산 1회당 평균 이동이 0.45회입니다.
- 정렬 단계에서도 차이가 있습니다. 퀵 정렬은 `swap`이 많아 491,876회 이동했습니다. AVL은 노드마다 값을 한 번만 저장하므로 18,146회(서로 다른 값의 수)만 이동했습니다.

### 5.3 배열과 AVL 트리의 메모리 사용량 차이
- 20,000개에서 배열은 **86,580 Byte**, AVL은 **623,248 Byte**를 사용했습니다. AVL이 **약 7.2배** 큽니다.
- **배열:** 원소 하나에 `int` 4 Byte만 사용합니다. 퀵 정렬의 재귀 스택은 수백 Byte로 작습니다. 그래서 최대 사용량은 삽입이 끝난 뒤 가장 많아진 원소 수(21,645개 × 4 Byte)로 정해졌습니다.
- **AVL:** 노드 하나가 32 Byte입니다. 이 중 데이터는 4 Byte뿐이고, 나머지는 중복 개수(4), 높이(4), 패딩(4), 자식 포인터 2개(16)입니다. 데이터 1개를 저장하려고 8배의 공간을 쓰는 셈입니다.
- 중복 값을 `count`로 묶었기 때문에 노드 수는 원소 수보다 적습니다. 값 범위(10만)에 비해 데이터가 많을수록 중복이 늘어 이 절약 효과가 커집니다. 그래도 노드 하나의 오버헤드가 커서 배열보다 훨씬 많은 메모리를 씁니다.
- 실제로는 `malloc`이 블록마다 관리 정보를 붙이므로, AVL의 실제 메모리 사용량은 이 계산값보다 더 클 수 있습니다.

### 5.4 데이터 크기 증가에 따른 성능 변화
n이 2배가 될 때 삽입·삭제 단계의 비교 횟수가 몇 배가 되었는지 보면 다음과 같습니다.

| 구간 | 배열 삽입·삭제 비교 | AVL 삽입·삭제 비교 |
|---|---:|---:|
| 1,000 → 2,000 | 3.94배 | 2.20배 |
| 2,000 → 4,000 | 4.15배 | 2.17배 |
| 4,000 → 8,000 | 4.12배 | 2.18배 |
| 8,000 → 16,000 | 4.00배 | 2.13배 |

- **배열은 약 4배씩 증가합니다.** 연산 수 m이 n의 20%로 2배가 되고, 연산 1회의 비용(선형 탐색·이동)도 n에 비례해 2배가 되기 때문입니다. 즉 O(m · n) = **O(n²)** 입니다. 총 시간도 2,000 → 4,000 → 8,000 → 16,000에서 약 3.4배, 2.4배, 3.1배로 n보다 훨씬 빠르게 늘었습니다.
- **AVL은 약 2.1~2.2배씩 증가합니다.** 연산 수는 2배가 되지만 연산 1회의 비용은 log n으로 조금만 늘어나기 때문입니다. 즉 O(m log n) = **O(n log n)** 입니다. 총 시간도 n에 거의 비례해서 늘었습니다(8,000 → 16,000에서 1.9배).
- 그래서 두 방법의 시간 차이는 n이 커질수록 벌어집니다. 1,000개에서는 배열이 1.4배 빨랐고, 4,000개에서는 AVL이 1.9배, 20,000개에서는 6.2배 빨랐습니다. 데이터가 더 커지면 이 차이는 계속 커집니다.
- 메모리는 두 방법 모두 O(n)으로 증가했습니다. AVL과 배열의 비율은 8.0배(1,000개)에서 7.2배(20,000개)로 조금씩 줄었습니다. 데이터가 많아질수록 중복 값이 늘어 AVL 노드 수가 원소 수보다 상대적으로 적어지기 때문입니다.

### 5.5 삽입·삭제가 반복되는 환경에서 유리한 자료구조
**삽입·삭제가 반복되는 환경에서는 AVL 트리가 유리합니다.**

| 연산 | 정렬된 배열 | AVL 트리 |
|---|---|---|
| 정렬(구성) | O(n log n), 상수 작음 | O(n log n), 할당 비용 있음 |
| 탐색 (선형 탐색 기준) | O(n) | O(log n) |
| 삽입 | O(n) 탐색 + O(n) 이동 | O(log n) 탐색 + O(1) 이동 + O(log n) 균형 복구 |
| 삭제 | O(n) 탐색 + O(n) 이동 | O(log n) |
| 추가 메모리 | 원소당 4 Byte | 원소(노드)당 32 Byte |

- **이유 1 — 탐색 비용:** AVL은 회전으로 높이를 O(log n)으로 유지하므로, 값의 위치를 찾는 데 약 log n번만 비교합니다. 실험에서 연산 1회당 비교가 배열은 약 10,389회, AVL은 21.4회였습니다.
- **이유 2 — 이동 비용:** 배열은 연속 저장 구조라서 중간에 넣거나 빼면 뒤의 원소를 모두 옮겨야 합니다. AVL은 포인터만 바꾸면 되므로 데이터를 거의 옮기지 않습니다. 실험에서 연산 1회당 이동이 배열은 약 6,326회, AVL은 0.45회였습니다.
- **이유 3 — 확장성:** 배열의 비용은 O(n²)으로 커지므로, 데이터와 연산이 많을수록 AVL과의 차이가 계속 벌어집니다.
- **배열이 나은 경우:** 데이터를 한 번 정렬한 뒤 거의 바꾸지 않거나, 데이터가 아주 적은 경우(이번 실험의 n = 1,000)입니다. 메모리가 부족한 환경에서도 배열이 낫습니다. 배열은 메모리가 1/7 수준이고, 연속 메모리라서 캐시 효율이 좋습니다. 또 이진 탐색을 쓰면 탐색만은 O(log n)으로 줄일 수 있습니다. 하지만 이동 비용 O(n)은 배열 구조 때문에 피할 수 없습니다.

## 6. 결론
1. **정렬만** 할 때는 퀵 정렬이 비교 횟수(약 18% 적음)와 시간(약 2배 빠름) 모두 유리했습니다. 연속 메모리와 할당 비용이 없다는 점 때문입니다.
2. **삽입·삭제가 반복되면** AVL이 크게 앞섰습니다. 20,000개에서 비교 89배, 이동 1,293배, 시간 6.2배 차이입니다. 배열의 선형 탐색과 원소 이동이 전체 비용의 대부분을 차지했습니다.
3. **메모리**는 배열이 약 7배 적었습니다. AVL 노드의 포인터·높이·개수 필드가 오버헤드입니다.
4. n이 커질수록 배열은 O(n²), AVL은 O(n log n)으로 증가해 차이가 계속 벌어졌습니다. 그래서 **데이터가 자주 바뀌는 환경에서는 AVL 트리**, 정적이고 메모리가 중요한 환경에서는 정렬된 배열이 적합합니다.
5. **한계:** 시간은 한 환경에서 20회 평균으로 측정했고, 메모리는 계산으로 구한 추정치입니다. 또 값 범위가 넓어 삭제의 약 80%가 "값 없음"으로 끝났으므로, 실험 중 데이터 개수가 계속 늘어났습니다.
